# DECISIONS — журнал архитектурных решений

Журнал фиксирует ключевые архитектурные решения проекта: что решили, почему, какие альтернативы отклонили.
Записи добавляются снизу, ID не переиспользуются, отменённые решения не удаляются — меняется статус на «Заменено на ADR-XXX».

## ADR-001. Clean Architecture с пятью слоями (включая Common)

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Учебный проект, надо показать разделение ответственности.

**Решение:** Domain, Common, Application, Infrastructure, API. Зависимости — только внутрь.

**Альтернативы:**
- Один проект с папками — проще, но не показывает границы.
- Vertical Slice — другой подход, конфликтует с целью практики слоёв.
- Микросервисы — избыточно.

**Последствия:** Пять проектов в solution; поддержание границ вручную, без анализатора.

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Выбор платформы и стиля API.

## ADR-003. EF Core + MSSQL, без Docker в MVP

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Хранение данных и способ запуска БД.

**Решение:** EF Core + локальная установка SQL Server. Docker отложен.

**Альтернативы:**
- PostgreSQL — тоже хорош, но MSSQL ближе к целевому стеку.
- SQLite — не показывает реальную работу с MSSQL.
- Docker — лишний слой для учебного MVP.

**Последствия:** MSSQL надо установить локально; инструкция по запуску должна это учитывать.

## ADR-004. Handlers вручную через DI, без MediatR

**Дата:** 2026-10-12
**Статус:** Заменено на ADR-025

**Контекст:** Как вызывать use case'ы.

**Решение:** Свой интерфейс `IHandler<TRequest, TResponse>`, регистрация в DI, вызов из контроллера напрямую.

**Альтернативы:**
- MediatR — магия, лишний слой абстракции.
- Minimal API с endpoint-фильтрами — не подходит под Controllers.

**Последствия:** Явные зависимости в конструкторе контроллера; чуть больше кода регистрации; зато всё видно.

## ADR-005. Repository + IUnitOfWork

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Как абстрагировать доступ к данным.

**Решение:** `ITaskRepository` для задач, `IUnitOfWork` для сохранения. Интерфейсы в Application, реализации в Infrastructure.

**Альтернативы:**
- DbContext напрямую в Handler'ах — быстрее, но утекает EF Core в Application.
- Generic Repository — мёртвые методы, не нужен для одной сущности.

**Последствия:** Явное разделение чтения и сохранения; Handler сам решает, когда вызвать `SaveChangesAsync`.

## ADR-006. FluentValidation для входных DTO

**Дата:** 2026-10-12
**Статус:** Заменено на ADR-025

**Контекст:** Как валидировать входящие данные.

**Решение:** FluentValidation-валидаторы рядом с Handler'ами, вызов внутри Handler'а.

**Альтернативы:**
- DataAnnotations — слабее, привязаны к ASP.NET.
- Ручные проверки в Handler'е — дублирование.
- Валидация в Middleware / pipeline — магия.

**Последствия:** Валидаторы — отдельные классы; сообщения согласованы с Domain-инвариантами.

## ADR-007. Централизованная конфигурация сборки

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Пять проектов, дублирование свойств.

## ADR-008. TreatWarningsAsErrors=true, IDE0005 как suggestion

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Строгий режим компилятора и конфликт Roslyn.

**Решение:** `TreatWarningsAsErrors=true`; IDE0005 (unused usings) — suggestion, потому что warning требует `GenerateDocumentationFile=true`, что порождает поток CS1591.

**Альтернативы:**
- `TreatWarningsAsErrors=false` — мягче, но пропускает проблемы.
- Включить `GenerateDocumentationFile` — не хотим XML-доки во всех проектах.

**Последствия:** Сборка падает на предупреждениях; unused usings контролируется только в IDE.

## ADR-009. Исключения для бизнес-ошибок

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Как выражать ожидаемые ошибки.

**Решение:** `DomainValidationException` (400), `DomainConflictException` (409), `ValidationException` (400, FluentValidation), `NotFoundException` (404). Единый базовый `DomainException`.

**Альтернативы:**
- `Result<T>` — чище, но многословно для MVP.
- Коды ошибок — нужен маппинг в Middleware.
- Всё через один Exception — не различить в Middleware.

**Последствия:** Middleware маппит по типу; исключения — контроль потока для ожидаемых сценариев.

## ADR-023. Роль AGENTS.md и короткие промпты

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Промпты для агента дублировали правила, которые уже зафиксированы в `AGENTS.md` и `docs/*.md`. Это замедляло работу и раздувало промпты.

**Решение:** Правила, действующие для любой задачи, живут в `AGENTS.md`. Спецификации — в `docs/*.md`. Промпт содержит только: задачу, ссылки на релевантные разделы, ограничения именно этого шага, критерий готовности и формат отчёта. Формат отчёта зафиксирован в `AGENTS.md` §8 и повторяется в промпте только при отличиях.

**Альтернативы:**
- Длинные промпты с полным контекстом — дублирование, рассинхронизация при изменении правил.
- Один большой AGENTS.md без ссылок на docs — теряется структура «правила / спецификации / задача».

**Последствия:** Промпты сократились в 3–5 раз. Требуется дисциплина: перед задачей агент читает релевантный документ (маппинг в `AGENTS.md` §3).

## ADR-024. TaskDto.Status — enum, конвертация в строку на уровне API

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** `TaskItemStatus` — enum в Domain. В JSON-ответе API статус — строка (`"Todo"`). Нужно решить, на каком слое enum превращается в строку.

**Решение:** `TaskDto.Status` хранит `TaskItemStatus`. Enum → string выполняется на уровне API при маппинге `TaskDto → TaskResponse`. Сериализацию обеспечивает глобальный `JsonStringEnumConverter` (ADR-011).

**Альтернативы:**
- `TaskDto.Status` — `string`, конвертация в Handler'е. Теряется типобезопасность; знание о формате API протекает в Application; формат растекается по всем handler'ам.

**Последствия:** Application оперирует enum'ом, сравнения типобезопасны. Формат статуса — в одном месте (API + `JsonStringEnumConverter`). `TaskDto` не готов к прямой сериализации — но он и не должен: между `TaskDto` и JSON всегда есть `TaskResponse`.

## ADR-025. MediatR и pipeline behaviors

**Дата:** 2026-10-12
**Статус:** Принято
**Заменяет:** ADR-004, ADR-006, ADR-017

**Контекст:** Изначально handlers вызывались через свой интерфейс `IHandler<TRequest, TResponse>`, а валидация выполнялась внутри handler'а вручную (ADR-004, ADR-006). При переходе к Этапу 3 стало ясно, что валидация дублируется в каждом write-handler'е, а контроллер вынужден инжектить по одному handler'у на каждый сценарий. MediatR решает обе проблемы: единый `IMediator.Send`, pipeline behaviors для сквозной логики.

**Решение:** Ввести MediatR. Request-модели реализуют `IRequest<TResponse>`, handlers — `IRequestHandler<TRequest, TResponse>`. Валидация вынесена в `ValidationBehavior<TRequest, TResponse>` — единая точка, работает для всех команд, у которых есть `IValidator<TRequest>`. Свой `IHandler` и свой `Unit` удалены, используется `MediatR.Unit`.

**Альтернативы:**
- Свой pipeline через декораторы `IHandler` — требует ручной регистрации декораторов для каждого handler'а, либо зависимость на Scrutor; по сути — повторение MediatR худшего качества.
- Оставить валидацию внутри handler'а (ADR-006) — дублирование, ручной вызов в каждом write-handler'е.
- MediatR без pipeline, только `Send` — теряется основная ценность MediatR.

**Последствия:**
- Контроллер зависит только от `IMediator`, а не от N handler'ов.
- Валидация — единая, в `ValidationBehavior`, handler'ы о ней не знают.
- Появляется внешняя зависимость (MediatR), «магия» `Send` — что именно произойдёт, видно только по DI-регистрации и pipeline.
- `Unit` теперь из MediatR.
- Handler'ы реализуют `IRequestHandler<TRequest, TResponse>` (не свой интерфейс).
- Регистрация handler'ов автоматическая через `AddMediatR(...)`.

## ADR-026. Исключение .editorconfig для миграций EF Core

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** EF Core генерирует миграции с block-scoped namespace. Наш `.editorconfig` требует file-scoped namespace (`csharp_style_namespace_declarations = file_scoped:warning` + `EnforceCodeStyleInBuild=true` + `TreatWarningsAsErrors=true`), из-за чего сгенерированные файлы ломают сборку (IDE0161).

**Решение:** Добавить в `.editorconfig` исключение для папки `src/Backend/PS.TaskTracker/PS.TaskTracker.Infrastructure/Migrations/*.cs` — отключить правило IDE0161.

**Альтернативы:**
- Править namespace в каждом новом файле миграции вручную — трудозатратно, забывается, ломает авторегенерацию.
- Отключить `TreatWarningsAsErrors` — слишком грубо, теряем контроль над всем проектом.
- Отключить `EnforceCodeStyleInBuild` — теряем контроль стиля на CI.

**Последствия:** Миграции EF Core не подчиняются правилу file-scoped namespace. Все остальные файлы — подчиняются. Новые миграции не требуют ручной правки.

## ADR-027. Swashbuckle.AspNetCore вместо Microsoft.AspNetCore.OpenApi

**Дата:** 2026-10-13
**Статус:** Принято

**Контекст:** В API изначально стоял `Microsoft.AspNetCore.OpenApi` — новый минималистичный пакет от Microsoft. Он даёт `AddOpenApi()` / `MapOpenApi()`, но не имеет UI. Для интерактивной проверки endpoints нужен Swagger UI.

**Решение:** Заменить `Microsoft.AspNetCore.OpenApi` на `Swashbuckle.AspNetCore`. Swashbuckle даёт полный набор: `AddSwaggerGen()`, `UseSwagger()`, `UseSwaggerUI()`.

**Альтернативы:**
- Оставить `Microsoft.AspNetCore.OpenApi` + добавить отдельный UI-пакет — два пакета для одной задачи.
- NSwag — другая библиотека, менее распространена в .NET 10.

**Последствия:** Один пакет вместо двух. Swagger UI доступен в Development. Стандартный подход, широко используется.

## ADR-028. Игнорирование npm audit по braces в dev-зависимостях

**Дата:** 2026-10-13
**Статус:** Принято

**Контекст:** `npm audit` в frontend-проекте сообщает 4 уязвимости high severity в пакете `braces` (GHSA-vfj7-8cjw-p6xm). Пакет приходит транзитивно через `@vue/eslint-config-typescript` → `fast-glob` → `micromatch` → `braces`.

**Решение:** Игнорировать. Уязвимость затрагивает только ESLint (dev-инструмент), не приложение. `npm audit fix --force` понизит `@vue/eslint-config-typescript` до `14.0.1`, что может сломать линтер.

**Альтернативы:**
- `npm audit fix --force` — ломает версии пакетов, риск сломать lint.
- Удалить ESLint — теряем контроль качества кода.
- Ждать обновления `@vue/eslint-config-typescript` — единственный безопасный путь.

**Последствия:** Предупреждения в `npm audit` остаются. Проверять `npm audit` перед деплоем в прод (вне MVP).

## ADR-029. axios как HTTP-клиент frontend

## ADR-030. CORS на бэкенде для локальной разработки

**Дата:** 2026-10-13
**Статус:** Принято

**Контекст:** Frontend работает на `http://localhost:5173`, backend — на `http://localhost:5029`. Браузер заблокирует кросс-доменные запросы без CORS.

**Решение:** Настроить CORS на бэкенде в `Program.cs`. Политика `Frontend`: разрешить origin `http://localhost:5173`, любые заголовки и методы.

**Альтернативы:**
- Прокси в Vite (`server.proxy`) — работает только в dev, при деплое всё равно нужен CORS.
- Отключить CORS на бэкенде — небезопасно, не работает.

**Последствия:** В dev-режиме frontend свободно обращается к API. При деплое в прод — расширить список origins или вынести в конфигурацию.

## ADR-031. Требование .NET 10 SDK (не только Runtime)

**Дата:** 2026-10-14
**Статус:** Принято

**Контекст:** При попытке сборки возникла ошибка `NETSDK1141`: SDK 10 не найден. Runtime 10.0.13 был установлен, но SDK 10.0.4xx отсутствовал — были только 9.0.307 и 11.0.100-rc.2. `global.json` требует 10.0.401 с `rollForward: latestFeature`, что не находит SDK.

**Решение:** Проект требует **.NET 10 SDK**, не только Runtime. Зафиксировать в `README.md` раздел «Требования» с явным указанием. Установлен SDK 10.0.402.

**Альтернативы:**
- Обновить `global.json` до 11.0.100 — SDK 11 в статусе RC, нестабильно; потребовалась бы смена TFM на `net11.0`.
- Понизить до .NET 9 — конфликт с `net10.0` в проектах.

**Последствия:** При развёртывании на новой машине — ставить именно .NET 10 SDK. Runtime недостаточно. Проверка: `dotnet --list-sdks` должен содержать `10.0.4XX`.
