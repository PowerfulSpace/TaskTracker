# DECISIONS — журнал архитектурных решений

Журнал фиксирует ключевые архитектурные решения проекта: что решили, почему, какие альтернативы отклонили.
Записи добавляются снизу, ID не переиспользуются, отменённые решения не удаляются — меняется статус на «Заменено на ADR-XXX».

## ADR-001. Clean Architecture с четырьмя слоями + Common

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Учебный проект, надо показать разделение ответственности.

**Решение:** Domain, Common, Application, Infrastructure, API. Зависимости — только внутрь.

**Альтернативы:**
- Один проект с папками — проще, но не показывает границы.
- Vertical Slice — другой подход, конфликтует с целью практики слоёв.
- Микросервисы — избыточно.

**Последствия:** Пять проектов в solution; поддержание границ вручную, без анализатора.

## ADR-002. C# / .NET 10, ASP.NET Core Controllers

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Выбор платформы и стиля API.

**Решение:** .NET 10, Controllers.

**Альтернативы:**
- Minimal API — проще для мелких API, хуже для группировки.
- .NET 8 LTS — стабильнее, но не даёт практики с новым.

**Последствия:** Свежая платформа, актуальные практики.

## ADR-003. EF Core + MSSQL, без Docker в MVP

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Хранение данных и способ запуска БД.

**Решение:** EF Core + локальная установка SQL Server. Docker отложен.

**Альтернативы:**
- PostgreSQL — тоже хорош, но MSSQL ближе к целевому стеку.
- SQLite — не показывает реальную работу с MSSQL.
- Docker — лишний слой для учебного MVP.

**Последствия:** MSSQL надо установить локально; инструкция по запуску должна это учитывать.

## ADR-004. Handlers вручную через DI, без MediatR

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Как вызывать use case'ы.

**Решение:** Свой интерфейс `IHandler<TRequest, TResponse>`, регистрация в DI, вызов из контроллера напрямую.

**Альтернативы:**
- MediatR — магия, лишний слой абстракции.
- Minimal API с endpoint-фильтрами — не подходит под Controllers.

**Последствия:** Явные зависимости в конструкторе контроллера; чуть больше кода регистрации; зато всё видно.

## ADR-005. Repository + IUnitOfWork

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Как абстрагировать доступ к данным.

**Решение:** `ITaskRepository` для задач, `IUnitOfWork` для сохранения. Интерфейсы в Application, реализации в Infrastructure.

**Альтернативы:**
- DbContext напрямую в Handler'ах — быстрее, но утекает EF Core в Application.
- Generic Repository — мёртвые методы, не нужен для одной сущности.

**Последствия:** Явное разделение чтения и сохранения; Handler сам решает, когда вызвать `SaveChangesAsync`.

## ADR-006. FluentValidation для входных DTO

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Как валидировать входящие данные.

**Решение:** FluentValidation-валидаторы рядом с Handler'ами, вызов внутри Handler'а.

**Альтернативы:**
- DataAnnotations — слабее, привязаны к ASP.NET.
- Ручные проверки в Handler'е — дублирование.
- Валидация в Middleware / pipeline — магия.

**Последствия:** Валидаторы — отдельные классы; сообщения согласованы с Domain-инвариантами.

## ADR-007. Централизованная конфигурация сборки

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Пять проектов, дублирование свойств.

**Решение:** `Directory.Build.props` (TFM, LangVersion, Nullable, ImplicitUsings, TreatWarningsAsErrors), `Directory.Packages.props` (CPM), `global.json`, `.editorconfig`. В `.csproj` — только ссылки и специфика.

**Альтернативы:**
- Держать настройки в каждом `.csproj` — дублирование.
- Без CPM — версии плывут.

**Последствия:** Единые настройки; `.csproj` минималистичные.

## ADR-008. TreatWarningsAsErrors=true, IDE0005 как suggestion

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Строгий режим компилятора и конфликт Roslyn.

**Решение:** `TreatWarningsAsErrors=true`; IDE0005 (unused usings) — suggestion, потому что warning требует `GenerateDocumentationFile=true`, что порождает поток CS1591.

**Альтернативы:**
- `TreatWarningsAsErrors=false` — мягче, но пропускает проблемы.
- Включить `GenerateDocumentationFile` — не хотим XML-доки во всех проектах.

**Последствия:** Сборка падает на предупреждениях; unused usings контролируется только в IDE.

## ADR-009. Исключения для бизнес-ошибок

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Как выражать ожидаемые ошибки.

**Решение:** `DomainValidationException` (400), `DomainConflictException` (409), `ValidationException` (400, FluentValidation), `NotFoundException` (404). Единый базовый `DomainException`.

**Альтернативы:**
- `Result<T>` — чище, но многословно для MVP.
- Коды ошибок — нужен маппинг в Middleware.
- Всё через один Exception — не различить в Middleware.

**Последствия:** Middleware маппит по типу; исключения — контроль потока для ожидаемых сценариев.

## ADR-010. ProblemDetails (RFC 7807)

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Единый формат ошибок в API.

**Решение:** ProblemDetails с полями `type`, `title`, `status`, `detail`, `instance`; для 400 — дополнительно `errors`.

**Альтернативы:**
- Свой JSON-формат — проще, но нестандартно.
- Голый текст — неструктурированно.

**Последствия:** Стандартный контракт ошибок; интеграция с ASP.NET Core «из коробки».

## ADR-011. JsonStringEnumConverter глобально

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Как сериализовать `TaskItemStatus` в JSON.

**Решение:** `JsonStringEnumConverter` глобально, enum → строка `"Todo"` / `"InProgress"` / `"Done"`.

**Альтернативы:**
- Числа — нечитаемо в API.
- Кастомный конвертер — лишнее.

**Последствия:** Контракт API читаемый; при переименовании enum — ломающее изменение.

## ADR-012. Без AutoMapper, маппинг вручную

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Три уровня моделей (HTTP ↔ Application ↔ Domain).

**Решение:** Extension-методы `ToDto`, `ToDomain`, `ToResponse` вручную.

**Альтернативы:**
- AutoMapper — магия, сложно отлаживать.
- Mapster — то же.

**Последствия:** Явный маппинг; чуть больше кода; прозрачно для чтения.

## ADR-013. Богатая доменная модель

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Где живут бизнес-правила.

**Решение:** Логика переходов и инварианты в `TaskItem`. Handler только координирует.

**Альтернативы:**
- Анемичная модель — логика в Handler'ах, размазана.
- Domain services — избыточно для одной сущности.

**Последствия:** Домен защищает себя; Handler'ы тонкие.

## ADR-014. Complete() идемпотентен на Done

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Поведение повторного вызова `Complete()`.

**Решение:** На `Done` — без исключения, `UpdatedAtUtc` не меняется.

**Альтернативы:**
- 409 — строже, но раздражает клиента.
- Обновлять `UpdatedAtUtc` — искажает историю.

**Последствия:** Клиент может безопасно повторять вызов; правило зафиксировано в DOMAIN.md.

## ADR-015. DateTime utcNow параметром

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Работа со временем в Domain.

**Решение:** Время передаётся параметром в методы; никаких `DateTime.UtcNow` внутри Domain; без `IClock` в MVP.

**Альтернативы:**
- `DateTime.UtcNow` внутри — не тестируется.
- `IClock` / `TimeProvider` — лишний интерфейс для MVP.

**Последствия:** Домен детерминирован; тесты простые.

## ADR-016. Двойная валидация: Domain + Application

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Где проверять инварианты.

**Решение:** Domain проверяет всегда (последняя линия); FluentValidation в Application — для сообщений 400. Правила согласованы.

**Альтернативы:**
- Только Domain — неудобные 400.
- Только FluentValidation — Domain не защищён.

**Последствия:** Дублирование правил; Domain не доверяет Application.

## ADR-017. Unit как тип-заглушка

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Сценарии без результата (`DeleteTask`).

**Решение:** `IHandler<TRequest, Unit>`, `Unit` — пустой `readonly struct` в Application.

**Альтернативы:**
- Отдельный `IHandler<TRequest>` — два интерфейса.
- `Task` без дженерика — не вписывается в общий интерфейс.

**Последствия:** Единый интерфейс; `Unit` — общий приём, узнаваемый C#-разработчиками.

## ADR-018. Command / Query на уровне Application

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Именование request-моделей.

**Решение:** `*Command` для изменения, `*Query` для чтения. `*Request` — только HTTP-DTO в API.

**Альтернативы:**
- `*Request` везде — путаница с HTTP-DTO.
- Без суффиксов — `CreateTask` неясно, команда или DTO.

**Последствия:** По имени видно роль; соглашение отражено в ARCHITECTURE.md.

## ADR-019. .editorconfig с crlf

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Окончания строк.

**Решение:** `end_of_line = crlf` — окружение Windows-only в MVP.

**Альтернативы:**
- `lf` — кроссплатформенно, но локально неудобно.
- Без настройки — хаос.

**Последствия:** При появлении Linux/Mac-разработчиков или CI — пересмотреть.

## ADR-020. UpdateTaskRequest и CreateTaskRequest — разные типы

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** DTO создания и обновления сейчас совпадают по полям.

**Решение:** Два разных типа, не объединять.

**Альтернативы:**
- Один `TaskUpsertRequest` — экономия, но связывает контракты; разойдутся при развитии.

**Последствия:** Дублирование полей; свобода менять контракты независимо.

## ADR-021. PUT возвращает 200 + TaskResponse

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Что возвращать после `PUT /api/tasks/{id}`.

**Решение:** 200 OK + `TaskResponse` (включая обновлённый `UpdatedAtUtc`).

**Альтернативы:**
- 204 No Content — строже по REST, но клиенту нужен второй запрос.

**Последствия:** Клиент получает актуальное состояние одним вызовом.

## ADR-022. Common пустой в MVP

**Дата:** 2026-10-12
**Статус:** Принято

**Контекст:** Зачем нужен проект Common, если кода в нём нет.

**Решение:** Оставить пустым, задел на будущее (общие утилиты, логирование, константы).

**Альтернативы:**
- Удалить — ломает структуру solution при появлении общего кода.
- Наполнить «на будущее» — абстракции без обоснования.

**Последствия:** Пустой проект в solution; при появлении общего кода — место уже есть.
